INFINITE WATER - BUY WHEEL IMPLEMENTATION PLAN
================================================

Date: 20.08.2026
Feature: Buy Wheel system
Status: PLAN ONLY - DO NOT IMPLEMENT UNTIL THIS PLAN IS APPROVED/REQUESTED

Purpose
-------
Implement a player-driven wheel purchase system. The game starts with exactly one
working wheel: the FOURTH wheel location in the map. The other five wheel
locations are not purchased and display a small clickable "Buy Wheel" window.

Every wheel costs exactly $100. There is no increasing price and no requirement
to buy wheels in map order. The player may buy any currently unbought wheel.

The exact interaction is:

    Unbought wheel location
            |
            v
      [ Buy Wheel ]
            |
          click
            v
    +------------------------------+
    | Do you want to buy this      |
    | wheel for 100$?              |
    |                              |
    |          [ Yes ] [ No ]      |
    +------------------------------+

    No  -> confirmation closes; Buy Wheel remains.
    Yes -> verify $100 -> subtract $100 -> activate that specific wheel ->
           remove confirmation window and Buy Wheel display.

If the player does not have $100, the wheel must not be activated and the
player's money must not change.


============================================================
1. CURRENT REPOSITORY CONTEXT
============================================================

The canonical production scripts are under lowercase:

    idle-water/scripts/

The architecture document says systems belong in scripts/systems, UI belongs
in scripts/ui, and simulation orchestration remains separate. New files should
follow the canonical lowercase structure and the project's small-file rule.

Relevant existing systems:

   - idle-water/scripts/simulation/WaterWheelManager.cs
   - Currently has MaxWheelCount = 6.
   - Discovers wheel marker tiles using atlas coordinates X=7, Y=6.
   - Currently creates every discovered wheel immediately.
   - Owns wheel physics state, wheel visuals, stepping and energy tracking.

2. FluidSimulator
   - idle-water/scripts/simulation/FluidSimulator.cs
   - Creates EnergySystem and WaterWheelManager.
   - Finds the Environment TileMapLayer.
   - Creates a viewport-to-simulation mapping.

   - Calls wheel stepping and wheel energy tracking every physics frame.

3. EnergySystem
   - idle-water/scripts/simulation/EnergySystem.cs
   - Owns Energy and Dollars.
   - Dollars are already generated by selling energy.
   - Current conversion is exactly 10 Energy -> $1 per sale click.

   - A purchase method should be added for atomic dollar spending.

4. EconomyUi
   - idle-water/scripts/ui/EconomyUi.cs
   - Displays Energy and Dollars in TopUI.

5. WaterWheelVisual
   - idle-water/scripts/rendering/WaterWheelVisual.cs
   - Owns the pixel-art wheel visual.

6. Existing roadmap

   - This document supersedes the old generic description for the concrete
     Buy Wheel implementation specified here.


============================================================
2. CORE GAMEPLAY RULES
============================================================

2.1 Total wheel locations

There are up to six wheel marker locations in the map.

    Wheel 1
    Wheel 2
    Wheel 3
    Wheel 4  <- STARTING WHEEL
    Wheel 5
    Wheel 6

The implementation MUST NOT assume that the first wheel discovered by
TileMapLayer.GetUsedCells() is the starting wheel.

The starting wheel is explicitly the FOURTH wheel location in the stable wheel
location ordering.

2.2 Initial state

New game:

    Wheel 1 = unbought
    Wheel 2 = unbought
    Wheel 3 = unbought
    Wheel 4 = BOUGHT / ACTIVE
    Wheel 5 = unbought
    Wheel 6 = unbought

Exactly one wheel is active at startup.

2.3 Purchasing

Every unbought wheel costs:

    $100

There is no price scaling.
There is no prerequisite chain.
There is no "next wheel" restriction.
There is no requirement to buy Wheel 1 before Wheel 6.

Example:

    Player owns Wheel 4.
    Player has $100.
    Player clicks Wheel 1's Buy Wheel window.
    Player confirms Yes.
    Wheel 1 becomes active.

The resulting state is:

    Wheel 1 = active
    Wheel 2 = unbought
    Wheel 3 = unbought
    Wheel 4 = active
    Wheel 5 = unbought
    Wheel 6 = unbought

2.4 No button

Clicking No only closes the confirmation window.
The Buy Wheel display remains visible.
No money is removed.
The wheel remains unbought.

2.5 Yes button

Clicking Yes must perform one atomic purchase attempt:

    if Dollars >= 100:
        subtract 100 dollars
        mark selected wheel as bought
        activate selected wheel
        remove Buy Wheel display
        close confirmation
    else:
        do nothing to wheel ownership or dollars
        keep the wheel unbought

The implementation must not deduct money before confirming that the wheel can
actually be activated.


============================================================
3. IMPORTANT ARCHITECTURAL DECISION
============================================================

DO NOT represent progression as "number of unlocked wheels".

A single integer such as:

    UnlockedWheelCount = 2

would be wrong for this design because the player can buy wheels in arbitrary
map order and Wheel 4 starts active.

Instead, maintain per-location ownership:

    WheelPurchased[0]
    WheelPurchased[1]
    WheelPurchased[2]
    WheelPurchased[3]
    WheelPurchased[4]
    WheelPurchased[5]

Initial values:

    false, false, false, true, false, false

This also makes future wheel-specific upgrades possible.


============================================================
4. SEPARATE WHEEL LOCATIONS FROM ACTIVE WHEELS
============================================================

CURRENT PROBLEM
--------------
WaterWheelManager currently iterates environment marker cells and immediately
calls CreateWaterWheel(). This means discovery order and active-wheel state are
implicitly the same thing.

REQUIRED DESIGN
---------------
First discover and store all wheel locations.
Only then determine which locations are purchased.
Only purchased locations are instantiated as active wheel physics/visuals.

Recommended conceptual data:

    WheelLocation
        int Id
        Vector2 TileMapCell
        Vector2 SimulationPosition
        bool Purchased
        WaterWheelRuntime Runtime (nullable)

WaterWheelManager should own the runtime wheel objects, while a separate wheel
progression/state object should own persistent purchase state.

The exact type names may be adjusted to match the ongoing refactor, but the
separation of responsibilities must remain.


============================================================
5. STABLE WHEEL ORDER
============================================================

The implementation must establish a deterministic order for the six wheel
locations.

Do NOT rely blindly on the enumeration order returned by GetUsedCells().

Recommended approach:

1. Find all cells matching WheelTileAtlasX=7 and WheelTileAtlasY=6.
2. Convert each marker to its world/simulation position.
3. Sort the discovered wheel locations deterministically.
4. Assign IDs 1..6 from that sorted list.
5. Verify that the known fourth location is the intended starting wheel.

The exact sorting direction must be selected after inspecting the actual map
layout. If the existing map's intended wheel order is spatial (for example
left-to-right or top-to-bottom), use that order consistently.

IMPORTANT:
The implementation should include a clear comment/documentation explaining
which spatial ordering makes the fourth location the intended starting wheel.

Do not silently choose an ordering that changes the player's expected wheel
numbering.


============================================================
6. WATER WHEEL MANAGER CHANGES
============================================================

File:

    idle-water/scripts/simulation/WaterWheelManager.cs

Current responsibility:

    - Discover wheel marker tiles.
    - Create wheel physics.
    - Create wheel visuals.
    - Step wheel states.
    - Track energy generated by wheel rotation.

Required changes:

6.1 Discovery phase

Replace the current immediate-create behavior with:

    DiscoverWheelLocations(...)

which returns/stores all wheel locations without creating active wheels.

6.2 Activation phase

Add a method conceptually equivalent to:

    ActivatePurchasedWheels()

or

    InitializePurchasedWheels(...)

It should create runtime wheels only for locations marked purchased.

6.3 Individual activation

Add a method conceptually equivalent to:

    TryActivateWheel(int wheelId)

This must:

    - validate wheel ID
    - verify the wheel is currently unbought
    - create its FluidWheelState
    - create its wheel polygon colliders
    - create its WaterWheelVisual
    - add it to runtime collections
    - initialize its energy tracking correctly
    - mark it active only after successful creation

6.4 Do not rebuild all wheels after every purchase

Buying Wheel 2 must not destroy/recreate Wheel 4 or other active wheels.
Only the newly purchased wheel should be created.

6.5 Runtime indexing

Do not use a runtime wheel list index as the persistent wheel ID.
Runtime list indexes can change when wheels are purchased.
Use a stable wheel ID/location record instead.

6.6 Primary wheel assumptions

The current code has special handling for wheelStates[0] as the primary wheel.
This must be reviewed carefully.

After this feature, the primary active wheel is the map's fourth wheel, not
necessarily wheel ID 1.

The implementation must ensure that:

    - the starting Wheel 4 receives the required primary-wheel behavior
    - later purchases do not accidentally become the primary wheel
    - energy tracking remains correct for all active wheels
    - StepPrimaryWheel() and StepAdditionalWheels() do not depend on map ID 1

If the solver's CreateWheel() API fundamentally requires a first/primary wheel,
explicitly designate the starting Wheel 4 as the primary runtime wheel.


============================================================
7. ENERGY SYSTEM CHANGES
============================================================

File:

    idle-water/scripts/simulation/EnergySystem.cs

Add an atomic purchase API conceptually:

    public bool TrySpendDollars(double amount)

Required behavior:

    amount <= 0       -> true or reject according to existing economy convention
    Dollars < amount  -> false, no state change
    Dollars >= amount -> subtract amount, return true

The wheel system should use this API rather than modifying the private dollars
field directly.

The fixed wheel price should be a named constant, for example:

    public const double WheelPurchaseCost = 100.0;

Prefer keeping the economy transaction in EnergySystem and the decision about
which wheel to buy in the wheel progression layer.

8. WHEEL PURCHASE / PROGRESSION SYSTEM
============================================================

Recommended new responsibility:

    WheelPurchaseSystem
or
    WheelProgressionSystem

Location recommendation:

    idle-water/scripts/systems/

or another appropriate canonical gameplay-system location according to the
current refactor architecture.

Responsibilities:

    - store/coordinate per-wheel purchased state
    - know starting wheel ID = 4
    - know purchase cost = $100
    - expose IsWheelPurchased(id)
    - perform purchase transaction through EnergySystem
    - tell WaterWheelManager to activate the selected wheel
    - emit/update UI state after purchase

It must NOT draw the UI.
It must NOT directly implement fluid physics.
It must NOT create Button nodes.


============================================================
9. WORLD UI: BUY WHEEL DISPLAY
============================================================

Each unbought wheel gets a small clickable world UI element.

Text:

    Buy Wheel

The display should be positioned at/near the corresponding wheel location.
It must follow the same simulation/world-to-screen mapping as the wheel.

It should not be part of TopUI or BottomUI.

Recommended implementation:

    WheelPurchaseUi

or

    BuyWheelWorldUi

This UI class should receive plain data from the gameplay layer and should not
call PbfSolver directly.

The architecture rules specifically state that scripts/ui classes should not
call solver methods directly.

9.1 One display per unbought wheel

Initial screen:

    Wheel 1 -> [Buy Wheel]
    Wheel 2 -> [Buy Wheel]
    Wheel 3 -> [Buy Wheel]
    Wheel 4 -> active wheel, no Buy Wheel display
    Wheel 5 -> [Buy Wheel]
    Wheel 6 -> [Buy Wheel]

9.2 Clicking

Each Buy Wheel display must know its stable wheel ID.
Clicking it opens a confirmation window for THAT wheel.

9.3 After purchase

The selected Buy Wheel display is removed.
The newly created wheel is visible in its place.
No other Buy Wheel displays are removed.


============================================================
10. CONFIRMATION WINDOW
============================================================

Create a dedicated confirmation UI for wheel purchases.

Suggested class:

    BuyWheelConfirmationWindow

The window text must be exactly or visually equivalent to:

    Do you want to buy this wheel for 100$?

Buttons:

    Yes
    No

Behavior:

YES
---

    - Re-check current Dollars at click time.
    - Re-check that the selected wheel is still unbought.
    - Attempt the $100 transaction.
    - If successful, activate that wheel.
    - Close the confirmation window.
    - Remove the Buy Wheel display for that wheel.

NO
--

    - Close only the confirmation window.
    - Leave the Buy Wheel display intact.
    - Do not change money.
    - Do not change wheel state.

The confirmation window should not use a generic global UI state that prevents
other unrelated HUD functionality unless the existing UI architecture requires
that behavior. It is a contextual purchase confirmation.


============================================================
11. INSUFFICIENT MONEY
============================================================

The player may click Buy Wheel even when they have less than $100.

The confirmation window can still open, because it is a confirmation of the
purchase intent.

When Yes is pressed:

    if Dollars < 100
        purchase fails
        wheel remains unbought
        money remains unchanged

The final UI treatment for insufficient funds should be simple and non-invasive.
Recommended options, in order of preference:

1. Keep confirmation open and briefly indicate insufficient funds, OR
2. Close confirmation and leave Buy Wheel visible.

Do not introduce a large new error window unless needed by the UI design.

The implementation plan intentionally leaves the exact insufficient-funds
visual feedback flexible, but the economic result is not flexible.


============================================================
12. WORLD/SIMULATION COORDINATES
============================================================

The Main scene contains a GameView/SimulationViewport and the simulation uses a
mapping between scene/global coordinates and simulation coordinates.

Wheel marker positions are currently converted through a mapping before wheel
creation.

The Buy Wheel UI must use the same source wheel position and mapping.

Do not calculate UI positions independently from the wheel positions.

Recommended flow:

    Environment marker
          |
          v
    WheelLocation
       /       \
      /         \
     v           v
Simulation pos   World/UI anchor
     |           |
     v           v
Active wheel   Buy Wheel display

This prevents the button from drifting away from the actual wheel.


============================================================
13. Z-ORDER / INPUT
============================================================

The Buy Wheel UI must be clickable while the simulation continues rendering.

Requirements:

    - It must receive mouse/touch input.
    - It must be above the simulation visuals.
    - It must not block the entire simulation area.
    - Only its actual control rectangle should consume input.
    - Clicking elsewhere must not accidentally purchase a wheel.

Android compatibility:

    - Button/control must respond to touch input through Godot Control input.
    - Do not depend on hover-only behavior.
    - The confirmation Yes/No buttons must be comfortably tappable.


============================================================
14. PERSISTENCE
============================================================

Purchase state should eventually persist between sessions.

IMPORTANT CURRENT STATE:
The repository has EnergySystem and economy UI, but a finalized player save
system/GameState persistence layer is not currently the appropriate place to
assume without checking the latest refactor state.

Therefore implement persistence in two stages:

Stage A - gameplay implementation

    - Use a dedicated wheel purchase state object/service.
    - Default to Wheel 4 purchased when no saved state exists.
    - Keep state accessible to the runtime.

Stage B - save integration

    - Add the six boolean purchase states to the project's actual save/game
      state system when that system is implemented.
    - Load purchase state before wheel runtime initialization.
    - Save immediately after a successful purchase or through the game's normal
      save mechanism.

Do not create a second unrelated save system just for wheels.


============================================================
15. INITIALIZATION ORDER
============================================================

Required startup sequence:

    1. Create EnergySystem.
    2. Create simulation/PBF dependencies.
    3. Create WaterWheelManager.
    4. Discover ALL wheel marker locations.
    5. Load/default wheel purchase state.
    6. Ensure Wheel 4 is purchased for a new/default game.
    7. Activate only purchased wheels.
    8. Create Buy Wheel UI for every unpurchased location.
    9. Initialize wheel energy tracking AFTER all currently purchased wheels
       have been activated.
   10. Continue normal physics/rendering.

The exact ordering around existing FluidSimulator initialization may be adapted,
but the logical dependency must remain.


============================================================
16. ENERGY TRACKING AFTER DYNAMIC PURCHASE
============================================================

This is a critical technical requirement.

The current WaterWheelManager stores:

    previousWheelAngles
    wheelEnergyGeneratedThisFrame

and initializes them from the current wheel count.

When a new wheel is purchased at runtime, these arrays must be expanded or
reinitialized without losing valid previous-angle information for existing
wheels.

Preferred behavior:

    - Existing wheels keep their previous angle.
    - Newly activated wheel gets its current angle as its previous angle.
    - The purchase frame must not generate a huge artificial energy spike just
      because the tracking array was resized.

Test specifically for this.


============================================================
17. COLLIDER ACTIVATION
============================================================

An unpurchased wheel must NOT have active wheel physics colliders.

Buying the wheel must create exactly the same wheel blade and hub colliders
used by the current wheel implementation.

Do not create disabled wheel colliders for all five locked wheels unless there
is a concrete performance/architecture reason.

This is especially important because multiple wheels have previously had a
significant performance cost in the project.

The dynamic purchase implementation should therefore activate only the wheel
that was purchased.


============================================================
18. PERFORMANCE REQUIREMENTS
============================================================

Do not add per-frame expensive work for locked wheels.

Avoid:

    - Creating/destroying all six wheels every frame.
    - Rebuilding all wheel colliders after every purchase.
    - Searching the entire scene tree for every wheel every frame.
    - Recreating all Buy Wheel UI every frame.

Preferred:

    - Discover wheel locations once at startup.
    - Create each Buy Wheel UI once.
    - Create each physical wheel once when purchased.
    - Remove only the corresponding purchase UI after purchase.
    - Keep stable references.

The current project has already identified wheel collision as a performance
hotspot, so dynamic activation is preferable to running locked wheels in a
hidden/disabled-but-still-simulated state.

22. EDGE CASES
============================================================

[ ] Player clicks the same Buy Wheel display repeatedly.
    -> Only one confirmation should exist for that wheel.

[ ] Player opens confirmation, then spends money elsewhere before pressing Yes.
    -> Yes must re-check current Dollars.

[ ] Player presses Yes twice very quickly.
    -> Only one purchase may succeed.

[ ] Player buys Wheel 1 and then Wheel 1 UI is clicked again.
    -> Impossible because the Buy Wheel UI has been removed.

[ ] Player buys all five remaining wheels.
    -> No Buy Wheel displays remain.
    -> All six wheels are active.

[ ] Map contains fewer than six wheel markers.
    -> Do not create nonexistent wheels.
    -> Only discovered locations participate.

[ ] Map contains more than six markers.
    -> Respect MaxWheelCount = 6 unless game design changes later.

[ ] Wheel 4 marker cannot be found.
    -> Do not silently choose another starting wheel.
    -> Emit a clear warning/error and fail safely.

[ ] Save contains invalid wheel IDs.
    -> Ignore invalid entries and keep valid wheel state.

- Do not make Wheel 1 the starting wheel.
- Do not use TileMapLayer.GetUsedCells() iteration order as an implicit gameplay
  rule without establishing deterministic ordering.
- Do not make UI classes call PbfSolver directly.
- Keep wheel physics activation in WaterWheelManager or the appropriate wheel
  system layer.
- Keep money transactions in EnergySystem.
- Keep purchase UI in scripts/ui.
- Keep the implementation split into small responsibilities in accordance
  with the repository architecture.

The most important gameplay rule is:

    START WITH WHEEL 4.
    EVERY OTHER WHEEL IS INDIVIDUALLY BUYABLE FOR $100.
    BUY ANY WHEEL IN ANY ORDER.
