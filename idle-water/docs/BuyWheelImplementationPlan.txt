INFINITE WATER - BUY WHEEL IMPLEMENTATION PLAN
================================================

Date: 20.08.2026
Feature: Buy Wheel system
Status: IMPLEMENTATION STARTED

Purpose
-------
Implement a player-driven wheel purchase system. The game starts with exactly
one active wheel: the FOURTH stable wheel location in the map. The other five
locations are unbought and display a clickable "Buy Wheel" control.

Every wheel costs exactly $100. There is no increasing price, no prerequisite
chain, and no requirement to buy wheels in map order.

Core rules
----------
1. Up to six wheel marker locations are discovered.
2. Wheel IDs are stable location IDs, not runtime-list indexes.
3. Wheel 4 is the starting/primary wheel.
4. Initial ownership is:
       Wheel 1 = false
       Wheel 2 = false
       Wheel 3 = false
       Wheel 4 = true
       Wheel 5 = false
       Wheel 6 = false
5. Every unbought wheel costs exactly $100.
6. A purchase is allowed for any currently unbought wheel.
7. If the player has less than $100, nothing changes.
8. No closes the confirmation and leaves Buy Wheel visible.
9. Yes re-checks ownership and money, activates the selected wheel, spends
   $100, closes confirmation, and removes only that wheel's Buy Wheel control.

Architecture
------------
The implementation separates three responsibilities:

WaterWheelManager
    idle-water/scripts/simulation/WaterWheelManager.cs

    - Discovers wheel marker locations without automatically activating them.
    - Uses atlas coordinates X=7, Y=6.
    - Sorts locations deterministically by TileMap Y, then X.
    - Assigns stable IDs 1..6 after sorting.
    - Owns active FluidWheelState instances and WaterWheelVisual instances.
    - Activates one wheel at a time without rebuilding existing wheels.
    - Keeps runtime index 0 reserved for the explicitly activated starting Wheel 4.
    - Continues to own stepping and energy tracking.

WheelPurchaseSystem
    idle-water/scripts/systems/WheelPurchaseSystem.cs

    - Owns per-location purchase state.
    - Defaults Wheel 4 to purchased.
    - Does not use an unlocked-wheel count.
    - Checks the fixed $100 purchase price.
    - Uses EnergySystem.TrySpendDollars() for the economy transaction.
    - Requests activation from WaterWheelManager.
    - Creates/removes world purchase controls.
    - Does not implement fluid physics.

World purchase UI
    idle-water/scripts/systems/WheelPurchaseSystem.cs

    - WheelPurchaseWorldUi provides the small clickable "Buy Wheel" control.
    - The control is a world-space Control positioned from the same simulation
      position as the corresponding wheel.
    - This keeps the purchase display aligned with the wheel while the camera
      moves and avoids a separate UI coordinate calculation.

Confirmation UI
    idle-water/scripts/systems/WheelPurchaseSystem.cs

    - WheelPurchaseConfirmationWindow displays:
          Do you want to buy this wheel for 100$?
      with Yes and No buttons.
    - Yes re-checks the economy and wheel state.
    - No only closes the confirmation.
    - Insufficient funds keeps the confirmation open and shows a small
      "Not enough money. You need 100$." message.

Economy
-------
File:
    idle-water/scripts/simulation/EnergySystem.cs

Added:
    public const double WheelPurchaseCost = 100.0;
    public bool TrySpendDollars(double amount)

TrySpendDollars() is atomic from the economy's point of view:
    amount <= 0       -> succeeds without changing dollars
    dollars < amount  -> fails without changing dollars
    dollars >= amount -> subtracts the requested amount and succeeds

The existing 10 Energy -> $1 sale system remains unchanged.

Initialization
--------------
The existing FluidSimulator call to:

    waterWheelManager.CreateWaterWheelsFromEnvironment(...)

is intentionally kept compatible through:

    idle-water/scripts/simulation/WaterWheelManagerLegacyApi.cs

That compatibility bootstrap now:
    1. discovers all wheel locations,
    2. creates WheelPurchaseSystem,
    3. initializes the purchased starting Wheel 4,
    4. creates Buy Wheel controls for all other discovered locations,
    5. initializes wheel energy tracking.

This avoids duplicating initialization logic in FluidSimulator while allowing
the progression system to remain separate from the simulation solver.

Primary-wheel handling
---------------------
The old assumption that runtime wheel index 0 means map Wheel 1 has been
removed from the wheel creation logic.

Wheel 4 is explicitly activated first. It therefore occupies runtime index 0
and remains the primary solver wheel. Later purchases are appended as additional
runtime wheels and do not replace or recreate Wheel 4.

Stable ordering
---------------
Wheel locations are sorted by:
    1. TileMap Y ascending
    2. TileMap X ascending

IDs are assigned after sorting. The implementation documents that this
stable top-to-bottom/left-to-right ordering is the ordering used for the
"fourth wheel" starting-wheel rule.

Important verification still required in-game: confirm that the current map's
actual fourth marker under this ordering is the intended starting wheel.
If the map's intended spatial ordering differs, the comparator must be changed
before release.

Persistence
-----------
Current implementation stage:
    - Runtime ownership state exists in WheelPurchaseSystem.
    - A new runtime starts with Wheel 4 purchased.
    - No separate wheel save file/system has been introduced.

Future save integration:
    - Add the six purchase booleans to the project's real GameState/save layer.
    - Load purchase state before wheel runtime initialization.
    - Save immediately after successful purchases or through the normal save
      mechanism.

This intentionally avoids creating a second unrelated save system.

Android/input requirements
--------------------------
The purchase controls use Godot Button/Control input rather than hover-only
behavior, so they are compatible with mouse and touch input. Only the actual
control rectangle consumes input.
