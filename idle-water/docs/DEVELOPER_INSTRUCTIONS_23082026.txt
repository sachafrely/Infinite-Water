0. GODOT SCENE (.tscn) DECISION — READ THIS FIRST
============================================================

The UI architecture must stay simple. Do NOT create a separate .tscn for every UI Node or every visual element.

For the current UI work, these are the ONLY separate UI scene types that should be created:

1. Main.tscn
   Existing main game scene. This remains the overall composition root.

2. WheelDisplay.tscn
   Reusable scene for ONE wheel's UI display.
   It is instantiated six times, once for each logical wheel.

3. BuyWindow.tscn
   Self-contained Buy Wheel modal window.

4. UpgradeWindow.tscn
   Self-contained Upgrade Wheel modal window.

5. SettingsWindow.tscn
   Self-contained Settings modal window.

6. StatisticsWindow.tscn
   Self-contained Statistics modal window containing its graph Nodes.

These six scene types are sufficient for the current UI Pass 2 architecture.

IMPORTANT: Do NOT create separate scenes for Ui, TopUi, BottomUi, WheelUi, UiWindowManager, individual graphs, displays, buttons, labels, panels, or layout containers unless a future requirement clearly makes one of them an independently reusable/self-contained component.

SCENE DECISION RULE

Create a separate .tscn only when at least one of these is true:
- The component is a self-contained UI component with its own meaningful layout and behavior.
- The component is a reusable component that will be instantiated multiple times.
- The component is an independently shown/hidden modal or major UI window.
- Keeping it embedded would make the owning scene unnecessarily large or difficult to maintain.

Do NOT create a .tscn merely because a Node has a script, is visually important, or has several child Nodes.

The goal is a clean, understandable hierarchy — not maximum scene fragmentation.

SCENE COMPOSITION

Main.tscn
└── Ui
    ├── TopUi
    ├── BottomUi
    ├── WheelUi
    │   ├── Wheel1  ← WheelDisplay.tscn instance
    │   ├── Wheel2  ← WheelDisplay.tscn instance
    │   ├── Wheel3  ← WheelDisplay.tscn instance
    │   ├── Wheel4  ← WheelDisplay.tscn instance
    │   ├── Wheel5  ← WheelDisplay.tscn instance
    │   └── Wheel6  ← WheelDisplay.tscn instance
    ├── StatisticsWindow  ← StatisticsWindow.tscn instance
    ├── SettingsWindow    ← SettingsWindow.tscn instance
    ├── BuyWindow         ← BuyWindow.tscn instance
    ├── UpgradeWindow     ← UpgradeWindow.tscn instance
    └── UiWindowManager

TopUi, BottomUi and WheelUi are ordinary Nodes inside Main.tscn. They do NOT need their own scenes.

StatisticsGraph and EnergyPerWheelGraph are ordinary child Nodes inside StatisticsWindow.tscn. They do NOT need separate scenes at this stage.

UiWindowManager is an application-level coordinator, not a visual component, and therefore is an ordinary Node inside the UI hierarchy.

UiSettings.cs is a static configuration class and is NOT a scene.

DO NOT create:
- Ui.tscn
- TopUi.tscn
- BottomUi.tscn
- WheelUi.tscn
- StatisticsGraph.tscn
- EnergyPerWheelGraph.tscn
- Scenes for individual Labels, Buttons, Panels, MarginContainers, VBoxContainers, HBoxContainers, spacers, sliders, indicators, graph labels, or similar small UI pieces.

If a proposed new scene is not clearly justified by the rules above, keep the component as a child Node in its owning scene.

1. PURPOSE
============================================================

This document defines the Godot Node/Scene architecture to use before refactoring the existing UI scripts.

IMPORTANT
Create the required scene Nodes in the Godot editor first. Do not replace the existing UI in one large rewrite. Migrate existing behavior incrementally.

ARCHITECTURE RULE
A major UI component may have a dedicated script without having its own scene. A separate scene is reserved for reusable, self-contained, or independently managed UI components.

2. MAIN UI HIERARCHY

The existing Main.tscn remains the overall scene.

Its Ui area should contain:

  - UiWindowManager

The exact existing Main.tscn structure should be preserved where possible during migration.

11. WINDOW / MODAL COORDINATION

Node Type:
Node
Name:
UiWindowManager
Script:
UiWindowManager.cs

Place it directly inside the existing Ui hierarchy in Main.tscn.

It is NOT a separate scene.

Responsibilities:
- Track the active modal window.
- Ensure modal windows are in front.
- Close the active modal when clicking/touching outside it where appropriate.
- Prevent multiple modal windows from fighting for input.

Individual windows remain responsible for their own internal behavior.

12. UI SETTINGS

File:
UiSettings.cs

UiSettings remains a centralized static configuration class.

All shared values such as:
- BorderColor
- BorderSize
- ButtonBorderSize
- Button colors
- Enabled/disabled font colors
- Font sizes

must come from UiSettings.cs.

Do not introduce local copies of these values inside individual UI scripts unless a component has a deliberate unique visual requirement.

13. SCRIPT RESPONSIBILITY RULES

UI scripts should:
- Find/cache their child Nodes.
- Update text and visual state.
- Connect signals/events.
- React to game state.
- Position their own component when necessary.
- Request modal/window changes from UiWindowManager when appropriate.

UI scripts should NOT:
- Build an entire UI hierarchy from scratch.
- Duplicate shared UiSettings constants.
- Own unrelated windows.
- Duplicate wheel numbering logic.
- Duplicate global modal input handling.

A script does NOT automatically require a separate .tscn. Prefer ordinary child Nodes when a component is not reusable or independently managed.
