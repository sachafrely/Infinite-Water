0. GODOT SCENE (.tscn) DECISION — READ THIS FIRST
============================================================

For the current UI refactor, the following items MUST be separate Godot Scenes (.tscn):

1. UI ROOT
   Scene: UI.tscn
   Root Node: CanvasLayer named UI
   Script: UIController.cs
   Reason: This is the top-level UI composition and must provide a stable scene root.

2. TOP UI
   Scene: TopUI.tscn
   Root Node: Control named TopUI
   Script: TopUi.cs
   Contains: TopUIBackground, EnergyDisplay, DollarsDisplay, RainAmountDisplay.
   Reason: Persistent top-of-screen component with its own layout and behavior.

3. BOTTOM UI
   Scene: BottomUI.tscn
   Root Node: Control named BottomUI
   Script: BottomUi.cs
   Contains: BuyArea, UpgradeArea, SettingsButton, StatisticsButton and other persistent bottom controls.
   Reason: Persistent UI component with its own layout and interaction behavior.

4. WHEEL UI
   Scene: WheelUI.tscn
   Root Node: Control named WheelUI
   Script: WheelUi.cs
   Contains: Wheel1 through Wheel6.
   Reason: Dedicated repeated UI system with six logical wheel displays.

5. INDIVIDUAL WHEEL DISPLAY
   Scene: WheelDisplay.tscn
   Root Node: Control named WheelDisplay
   Script: WheelDisplay.cs
   Used as an instance for Wheel1 through Wheel6 inside WheelUI.tscn.
   Reason: The six wheels share the same structure and behavior and therefore must use one reusable scene rather than six copied hierarchies.
   IMPORTANT: Wheel number is data/instance state, not a reason to create six different scenes.

6. BUY WINDOW
   Scene: BuyWindow.tscn
   Root Node: PanelContainer named BuyWindow
   Script: BuyWindow.cs
   Reason: Independent modal window with its own layout and behavior.

7. UPGRADE WINDOW
   Scene: UpgradeWindow.tscn
   Root Node: PanelContainer named UpgradeWindow
   Script: UpgradeWindow.cs
   Reason: Independent modal window with its own layout and behavior.

8. SETTINGS WINDOW
   Scene: SettingsWindow.tscn
   Root Node: PanelContainer named SettingsWindow
   Script: SettingsWindow.cs
   Reason: Independent modal window with its own layout and behavior.

9. STATISTICS WINDOW
   Scene: StatisticsWindow.tscn
   Root Node: PanelContainer named StatisticsWindow
   Script: StatisticsWindow.cs
   Contains the graph component instances.
   Reason: Independent modal window with a substantial, self-contained layout.

10. STANDARD GRAPH COMPONENT
    Scene: StatisticsGraph.tscn
    Root Node: Control named StatisticsGraph
    Script: StatisticsGraph.cs
    Used for graph types that share the same point/graph structure.
    Reason: Reusable graph component with its own rendering/layout behavior.

11. ENERGY PER WHEEL GRAPH
    Scene: EnergyPerWheelGraph.tscn
    Root Node: Control named EnergyPerWheelGraph
    Script: EnergyPerWheelGraph.cs
    Reason: This graph has materially different bar-based behavior and therefore deserves its own scene instead of being forced into the generic graph scene.

The following items MUST NOT become separate Scenes merely because they are visible UI elements:

- Individual Labels
- Individual Buttons
- Individual Panels
- Individual PanelContainers used only as layout wrappers
- MarginContainers
- VBoxContainers / HBoxContainers
- Spacers
- Title labels
- Wheel number labels
- Price buttons
- Close buttons
- Individual graph labels/axis labels
- TopUIBackground
- EnergyDisplay
- DollarsDisplay
- RainAmountDisplay
- BuyArea / UpgradeArea when they only act as sections of BottomUI
- TiltSlider
- GravityIndicator
- Individual wheel buttons/labels inside WheelDisplay

These remain child Nodes inside their owning Scene and are controlled by the owning component script.

SCENE CREATION RULE

Create a separate .tscn when a UI component has its own meaningful layout + behavior/identity, is independently shown/hidden, is reused as an instance, or is a substantial self-contained component.

Do NOT create a .tscn for every Control. Scene-per-control would recreate the current UI architecture problem at a different level and make the hierarchy unnecessarily fragmented.

COMPOSITION RULE

The intended scene composition is:

UI.tscn
├── TopUI.tscn
├── BottomUI.tscn
├── WheelUI.tscn
│   ├── WheelDisplay.tscn × 6
├── StatisticsWindow.tscn
│   ├── StatisticsGraph.tscn
│   ├── StatisticsGraph.tscn / specialized graph instance as required
│   └── EnergyPerWheelGraph.tscn
├── SettingsWindow.tscn
├── BuyWindow.tscn
└── UpgradeWindow.tscn

UIWindowManager is NOT a separate scene. It is a Node directly inside UI.tscn because it is an application-level coordinator rather than a visual UI component.

UiSettings.cs is NOT a scene. It remains the centralized static UI configuration class.

Do not create additional .tscn files without first checking this rule. If a proposed component does not clearly meet the scene criteria above, keep it as a child Node of its owning Scene.

============================================================
1. PURPOSE
============================================================

This document defines the Godot Node/Scene architecture to create before refactoring the existing UI scripts.

IMPORTANT
Create these Nodes in the Godot editor first. Do not replace the existing UI in one large rewrite. The implementation should migrate existing behavior into these Nodes incrementally.

ARCHITECTURE RULE
A major UI component gets its own Node and dedicated script. A component becomes a separate Scene when it has its own layout, behavior, identity, or is reusable. Individual Labels, Buttons, Panels and containers normally remain children of their parent UI Scene rather than receiving their own scripts.

12. WINDOW / MODAL COORDINATION

Node Type:
Node
Name:
UIWindowManager
Script:
UiWindowManager.cs

Place it as a direct child of UI.

Responsibilities:
- Track the active modal window.
- Ensure modal windows are in front.
- Close the active modal when clicking/touching outside it where appropriate.
- Prevent multiple modal windows from fighting for input.

Individual windows remain responsible for their own internal behavior.

13. UI SETTINGS

File:
UiSettings.cs

UiSettings remains a centralized static configuration class.

All shared values such as:
- BorderColor
- BorderSize
- ButtonBorderSize
- Button colors
- Enabled/disabled font colors
- Font sizes

must come from UiSettings.cs.

Do not introduce local copies of these values inside individual UI scripts unless a component has a deliberate unique visual requirement.

14. SCRIPT RESPONSIBILITY RULES

UI scripts should:
- Find/cache their child Nodes.
- Update text and visual state.
- Connect signals/events.
- React to game state.
- Position their own component when necessary.
- Request modal/window changes from UIWindowManager when appropriate.

UI scripts should NOT:
- Build an entire UI hierarchy from scratch.
- Duplicate shared UiSettings constants.
- Own unrelated windows.
- Duplicate wheel numbering logic.
- Duplicate global modal input handling.

15. RECOMMENDED MIGRATION ORDER

1. Create UI root scene and UIWindowManager.
2. Create WheelUI scene and WheelDisplay scene; instance six wheels.
3. Create BuyWindow scene and attach BuyWindow.cs.
4. Migrate the current working Buy Window behavior.
5. Create UpgradeWindow scene and attach UpgradeWindow.cs.
6. Migrate the current working Upgrade Window behavior.
7. Create StatisticsWindow scene and its graph scene instances.
8. Implement EnergyPerWheelGraph scene.
9. Migrate SettingsWindow scene.
10. Migrate TopUI and BottomUI scenes.
11. Remove obsolete runtime UI construction only after each migration is verified.

16. TESTING REQUIREMENT

After every migration:
- Run on Windows.
- Verify mouse interaction.
- Verify outside-click behavior.
- Verify window layering.
- Verify enabled/disabled colors.
- Verify no duplicate UI is being created.

After the complete migration:
- Test Android touch input.
- Verify all six wheel numbers.
- Verify Buy and Upgrade windows display the correct wheel number.
- Verify all three statistics graphs.
