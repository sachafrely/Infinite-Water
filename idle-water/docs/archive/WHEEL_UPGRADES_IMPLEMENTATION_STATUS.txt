INFINITE WATER — WHEEL UPGRADES IMPLEMENTATION STATUS
Updated: 21.08.2026
Branch: feature/wheel-upgrades

CURRENT RUNTIME TEST STATUS
---------------------------
The current wheel-upgrades implementation has been tested in-game after the
latest implementation pass. The following observations are based on runtime
behavior rather than code inspection alone.

CONFIRMED WORKING
-----------------
- Buying an upgrade deducts the corresponding amount of money.
- Less Friction appears to work correctly: the upgraded wheel produces more
  energy / performs better in runtime testing.
- The upgrade purchase flow and per-upgrade economy behavior are functioning.

PARTIALLY VERIFIED
------------------
- More Efficient appears to increase energy generation, but this has not yet
  been verified with a controlled before/after measurement. Treat this as
  likely working, but NOT fully confirmed until an equivalent-input test is
  performed.

NOT YET CORRECT / NEEDS IMPLEMENTATION
--------------------------------------
- Bigger Paddles does not currently produce a clearly visible increase in
  paddle size during runtime testing.
- The current implementation changes the wheel visual BladeWidth, but the
  paddle/collider geometry used for physical interaction does not yet grow
  correctly with the upgrade.
- Bigger Paddles therefore must remain an incomplete feature until both the
  visual geometry and the physical paddle interaction are updated together.

CORRECT BIGGER-PADDLES PHYSICS REQUIREMENT
------------------------------------------
The implementation must treat paddle size as real physical geometry, not only
as a visual multiplier.

Required behavior:
- Keep immutable/base paddle dimensions for every wheel.
- Calculate effective paddle dimensions from the base dimensions and the
  Bigger Paddles level.
- Update the wheel's visual paddle geometry to the effective dimensions.
- Update the corresponding physical collision geometry to the SAME effective
  dimensions.
- Ensure the enlarged paddle occupies the correct position/orientation around
  the wheel's rotation axis.
- Ensure collision detection uses the enlarged geometry, so water particles can
  actually contact the newly added paddle area.
- Rebuild/update ONLY the selected wheel's paddle collider/geometry. Never
  rebuild the complete wheel collection or fluid simulation.
- Do not repeatedly scale an already-scaled collider or visual node. Always
  calculate from the immutable base dimensions and the upgrade level.
- Verify that the paddle's collision shape follows the wheel rotation and that
  its center/offset remains correct after resizing.
- Verify that enlarging a paddle does not create an unintended permanent offset,
  gap, overlap, or collision region unrelated to the paddle itself.

Recommended implementation sequence:
1. Identify the authoritative base paddle width/height/length values.
2. Store those base values separately from the runtime effective values.
3. Calculate EffectivePaddleSize = BasePaddleSize *
   (1.0 + 0.20 * BiggerPaddlesLevel).
4. Update the visual paddle geometry from the effective dimensions.
5. Recreate or resize only that wheel's FluidPolygonCollider / paddle collision
   geometry from the same effective dimensions.
6. Recalculate the collider's local polygon/vertices and local offset so the
   enlarged paddle remains centered correctly relative to the wheel.
7. Keep the existing wheel transform/rotation and fluid simulation instance.
8. Test particle interaction with the newly enlarged outer paddle area.

This is the required physics implementation for Bigger Paddles before the
upgrade can be marked fully complete.

UI ARCHITECTURE
---------------
DONE
- WheelUpgradeUi is created by EnergySystem using the same current-scene runtime
  creation pattern as WheelPurchaseUi.
- Upgrade UI is a child of the Main scene, outside the SimulationViewport.
- Upgrade entry ZIndex is 900 and is absolute, above the Environment TileMapLayer.
- Upgrade entry panels use ZIndex 901 and MouseFilter.Stop.
- Upgrade buttons are created entirely by script; no Godot editor node is required.
- Wheel positions are converted from simulation space to Main/GameView screen
  coordinates using the existing GameView/Camera mapping.
- The first owned wheel automatically gets an Upgrade entry while upgrades remain.
- The entry is associated with its deterministic wheel slot/index.

UPGRADE WINDOW
--------------
DONE
- Clicking Upgrade opens a dedicated WheelUpgradeWindow.
- Exactly three upgrade rows are provided in the required order:
  1. Bigger Paddles
  2. Less Friction
  3. More Efficient
- Each row has an independent level display and purchase button.
- Prices follow 20$, 30$, 40$ according to the individual upgrade's current level.
- Maxed upgrades show MAX and cannot be purchased.
- Insufficient money disables the purchase button.
- The window refreshes after a successful purchase.
- The window closes when all three upgrade types are maxed.

DATA / ECONOMY
--------------
DONE
- Added WheelUpgradeType enum.
- Added WheelUpgradeState with three independent 0..3 levels.
- Added per-wheel upgrade state to WaterWheelManager, indexed by wheel slot.
- Added HasAvailableUpgrades/GetUpgradeLevel/GetUpgradePrice/CanPurchaseUpgrade/
  PurchaseUpgrade APIs.
- Purchase validation checks ownership, max level, price, and available dollars.
- Existing EnergySystem dollars are used; no second currency was introduced.
- Valid purchases deduct money.

WHEEL EFFECTS
-------------
LESS FRICTION — RUNTIME RESULT: WORKING
- Less Friction reduces effective angular resistance and increases the wheel's
  maximum angular velocity according to the configured upgrade level.
- Runtime testing indicates the upgraded wheel performs better / generates more
  energy.

MORE EFFICIENT — RUNTIME RESULT: PROBABLY WORKING
- More Efficient applies the configured 100%/120%/140%/160% energy-generation
  multiplier to the individual wheel.
- Runtime behavior appears correct, but a controlled measurement is still
  required before marking this fully verified.

BIGGER PADDLES — RUNTIME RESULT: NOT COMPLETE
- The intended level multipliers are 100%, 120%, 140%, 160%.
- The current visual BladeWidth update is not sufficient: the paddle does not
  visibly appear larger in runtime testing.
- The physical paddle collision geometry also needs to be resized to match the
  visual geometry.
- See CORRECT BIGGER-PADDLES PHYSICS REQUIREMENT above and the implementation
  plan for the required geometry/collider approach.

SIMULATION SAFETY
-----------------
DONE
- No PbfSolver recreation.
- No ParticleData recreation.
- No SpatialHash recreation.
- No scene reload.
- No global energy multiplier.
- No full wheel collection rebuild when purchasing an upgrade.
- Upgrade state belongs to the selected wheel slot.

PERSISTENCE
-----------
NOT COMPLETE
- Upgrade levels are currently runtime state only.
- The existing project does not yet have a completed persistent save/load system.
- Do not invent a temporary incompatible save format as part of this upgrade work.

IMPORTANT UI LAYERING NOTE
--------------------------
The Upgrade UI intentionally follows the working Buy UI creation path:
EnergySystem creates the Control on the current Main scene with CallDeferred.
It must NOT be moved into FluidSimulation or GameView/SimulationViewport.
That keeps it outside the SubViewport and above the Environment TileMapLayer.
