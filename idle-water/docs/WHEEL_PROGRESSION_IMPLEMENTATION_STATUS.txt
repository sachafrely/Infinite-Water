IMPLEMENTED
------------

PHASE 1 — DISCOVERY / CREATION SEPARATION
Status: COMPLETE

- Wheel marker positions are collected before activation.
- Marker positions are converted to simulation coordinates.
- Positions are sorted deterministically by Y, then X.
- Maximum discovered wheel locations remains 6.
- Discovery does not instantiate all six wheel runtimes.

PHASE 2 — INITIAL ONE-WHEEL STATE
Status: COMPLETE

- A new game activates exactly one wheel.
- The current level's intended starting wheel is explicitly the third marker
  from the top (sorted index 2).
- That physical position becomes the primary runtime wheel.
- Other wheel locations remain inactive.
- Existing PBF simulation systems are not recreated.

PHASE 3 — DYNAMIC WHEEL ACTIVATION
Status: IMPLEMENTED — RUNTIME TEST PENDING

WaterWheelManager now provides:

- IsWheelUnlocked(index)
- UnlockedWheelCount
- CanUnlockNextWheel()
- GetNextLockedWheelIndex()
- GetWheelPosition(index)
- ActivateWheel(index)
- TryUnlockNextWheel()

Important behavior:

- Only one new wheel is activated per unlock.
- Existing FluidWheelState instances are not recreated.
- Existing wheel visuals are not recreated.
- The PbfSolver is not recreated.
- ParticleData is not recreated.
- SpatialHash is not recreated.
- FluidSimulationCoordinator is not recreated.
- Existing particles, rain and energy are not reset.

Runtime wheel indexes are deliberately kept separate from stable map-position
indexes. This is required because the starting wheel is physical position 2,
while runtime wheel index 0 is the primary wheel.

PHASE 4 — ECONOMY INTEGRATION
Status: IMPLEMENTED — RUNTIME TEST PENDING

EnergySystem now provides:

- WheelPurchaseCost = 20 dollars.
- TrySpendDollars(amount) for atomic spending.

TryUnlockNextWheel() follows the transaction safety rule:

1. Find the first locked wheel position.
2. Verify that $20 is available.
3. Activate the wheel in the existing simulation.
4. Spend $20 only after activation succeeds.
5. Return success/failure.

Insufficient money does not activate a wheel and does not change the dollar
balance.

PHASE 4 API BRIDGE
------------------
A partial FluidSimulator extension now exposes the progression system without
requiring UI code to access WaterWheelManager directly:

- ActiveWheelCount
- UnlockedWheelCount
- IsWheelUnlocked(index)
- CanUnlockNextWheel()
- TryPurchaseNextWheel()
- GetNextLockedWheelIndex()
- GetWheelPosition(index)

This keeps purchase/UI code above the simulation layer.

PHASE 5 — FIVE SMALL BUY WHEEL WINDOWS
Status: IMPLEMENTED — RUNTIME TEST PENDING

The requested UI design is five small purchase windows, one for each additional
locked wheel slot.

Behavior:

- The starting wheel has no Buy Wheel window.
- Five small windows are created for the five additional wheel slots.
- Each window is centered directly on the tile/position where its wheel will
  appear. There is no additional top-right or side offset.
- Every window always displays exactly two rows:
    Buy Wheel
    20$
- The purchase price is defined centrally by EnergySystem.WheelPurchaseCost.
- Only the next sequential purchase can be activated.
- Future locked windows remain visible but their purchase buttons are disabled.
- After a wheel is purchased, its window disappears and the next window becomes
  the available purchase target.
- The UI does not recreate or reset the fluid simulation.
- The UI is generated at runtime and does not require five manually duplicated
  UI nodes in the scene.

UI script:

- idle-water/Scripts/ui/WheelPurchaseUi.cs

The UI is bootstrapped alongside the existing EconomyUi from EnergySystem.

ENERGY TRACKING SAFETY
----------------------
When a wheel is activated, the existing per-wheel energy arrays are resized
without resetting the existing wheel data.

The newly activated wheel's previous-angle baseline is initialized to its
current angle. Therefore it should not generate artificial energy merely because
it was created.

PHASE 6 — PERSISTENCE
Status: NOT IMPLEMENTED

Wheel ownership is currently runtime-only. Restarting the game will return to
the fresh-game one-wheel state.

PHASE 7 — ENERGY VALIDATION
Status: IMPLEMENTED IN CODE / TEST PENDING

The new-wheel energy baseline protection is implemented. Runtime testing is
still required to confirm that:

- no artificial energy spike occurs on purchase;
- the new wheel generates energy from real rotation;
- existing wheels keep their normal production.

PHASE 8 — PERFORMANCE VALIDATION
Status: CODE SAFETY IMPLEMENTED / TEST PENDING

The implementation does not scan locked positions every frame and does not
rebuild the simulation when a wheel is activated.
