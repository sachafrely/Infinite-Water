PHASE 1 — GODOT UI NODE ARCHITECTURE
1. Create the agreed UI root hierarchy in Godot. DONE.
2. Create dedicated Nodes for major UI components and attach dedicated scripts. DONE / IN PROGRESS.
3. Move one component at a time from runtime-created Controls to scene Nodes.
4. Do not delete old construction code until the replacement Node is working and tested.
5. Establish exported Node references / GetNode references so scripts control existing Nodes instead of constructing complete UI trees.
6. Keep shared visual configuration centralized in UiSettings.cs.
7. Keep CenterUi as an ordinary Control Node that groups centered modal windows.
8. Keep UiWindowManager as an ordinary Node responsible for application-level modal coordination.

PHASE 4 — SCRIPT MIGRATION

Migrate the scripts in small, testable steps.

1. WheelDisplay.cs
   - Control the existing WheelDisplay Nodes.
   - Do not construct the complete wheel UI hierarchy at runtime.

2. BuyButton.cs and UpgradeButton.cs
   - Control the existing Button Nodes inside WheelDisplay.
   - Request the appropriate window/action rather than constructing duplicate UI.

3. WheelUi.cs
   - Manage the six WheelDisplay instances.
   - Establish wheel numbers 1–6 from left to right.
   - Provide the wheel identity used by Buy/Upgrade interactions.

4. BuyWindow.cs
   - Migrate the existing working Buy Window behavior to BuyWindow.tscn.
   - Control existing scene Nodes.
   - Display the supplied wheel number.

5. UpgradeWindow.cs
   - Migrate the existing working Upgrade Window behavior to UpgradeWindow.tscn.
   - Control existing scene Nodes.
   - Display the supplied wheel number.

6. TopUi.cs and display scripts
   - TopUi.cs owns the top-level layout/coordination.
   - RainDisplay.cs controls RainDisplay.
   - EnergyDisplay.cs controls EnergyDisplay.
   - MoneyDisplay.cs controls MoneyDisplay.

7. BottomUi.cs and button scripts
   - BottomUi.cs controls the persistent bottom area.
   - StatisticsButton.cs controls StatisticsButton.
   - SettingsButton.cs controls SettingsButton.
   - PrestigeButton.cs controls PrestigeButton.
   - SellEnergyButton.cs remains responsible for selling energy.

8. CenterUi.cs
   - Manage the centered window group/layout where appropriate.
   - Do not duplicate application-level modal state that belongs to UiWindowManager.

9. SettingsWindow.cs and settings child scripts
   - Migrate window-level behavior to SettingsWindow.cs.
   - Move remaining settings responsibilities into TiltSettingsContent.cs, AudioSettings.cs and MoreInfoButton.cs as appropriate.
   - Retire obsolete SettingsContent.cs responsibilities only after replacement behavior is verified.

10. StatisticsWindow.cs and graph scripts
    - StatisticsWindow.cs owns window-level behavior.
    - Each graph script owns only its graph Node.
    - Keep the third Energy-per-Wheel graph ordered Wheel 1 → Wheel 6.

11. PrestigeWindow behavior
    - Migrate behavior into the existing PrestigeWindow.tscn.

12. UiWindowManager.cs
    - Centralize modal state, input and window coordination.
    - Do not make it responsible for the internal content of individual windows.

13. Shared rendering/configuration
    - Keep UiSettings.cs centralized.
    - Use RenderedWindowBackground.cs and RenderedButtonBackground.cs where appropriate.

PHASE 5 — CLEANUP
1. Remove obsolete runtime UI construction only after each component has been migrated and tested.
2. Remove duplicate styling/constants that should come from UiSettings.cs.
3. Remove duplicate window-positioning logic where CenterUi or UiWindowManager now owns that responsibility.
4. Remove duplicate wheel-numbering logic.
5. Remove obsolete scripts only after all references are gone.
