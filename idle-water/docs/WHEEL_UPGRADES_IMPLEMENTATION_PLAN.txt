INFINITE WATER — WHEEL UPGRADES IMPLEMENTATION PLAN
Created: 21.08.2026
Updated: 21.08.2026
Branch: feature/wheel-upgrades

PURPOSE
-------
Implement per-wheel upgrades for every available/owned wheel without rebuilding
or destabilizing the existing fluid simulation.

The upgrade system is a gameplay layer above the existing WaterWheel/Wheel
simulation. Each wheel stores its own upgrade levels and applies those levels to
its own physical and energy-generation parameters.

The existing wheel progression system remains the ownership layer:
- A new game starts with the first wheel available/owned.
- Additional wheels can be purchased through the existing Buy Wheel system.
- Every owned wheel can show an Upgrade window whenever at least one upgrade
  level remains available.

CORE DESIGN PRINCIPLE
---------------------
Wheel upgrades modify the existing wheel instance in place.

Do NOT:
- recreate the PbfSolver
- recreate ParticleData
- recreate SpatialHash
- reload the scene
- recreate all wheels
- clear existing particles
- reset rain
- reset energy
- rebuild the complete simulation

An upgrade should only update the selected wheel's own parameters and then
refresh that wheel's UI/visual/physical state if necessary.

UPGRADE UI FLOW
---------------

1. FIRST AVAILABLE / OWNED WHEEL

As long as the selected wheel has at least one upgrade remaining, display an
"Upgrade" entry for that wheel.

The Upgrade entry should use a style similar to the existing "Buy" Window.
It must be associated with the correct wheel, not a global unrelated wheel.

The Upgrade UI must remain top-most, following the same working runtime creation
and layering approach as the Buy Wheel UI. It must not be placed inside the
SubViewport/SimulationViewport where the Environment TileMap can cover it.

2. CLICK "UPGRADE"

Open a dedicated Upgrade window containing exactly three upgrade possibilities
in this order:

1. Bigger Paddles
2. Less Friction
3. More Efficient

Each row contains:
- the upgrade name on the left
- a purchase button on the right
- the current price inside that button

3. AVAILABILITY

Each upgrade can be purchased independently.

A wheel may have any combination of the three upgrades.

Each individual upgrade has three possible levels:
- Level 0: not upgraded
- Level 1: +20%
- Level 2: +40%
- Level 3: +60%

Once an individual upgrade reaches level 3, its purchase button must become
unavailable/disabled or clearly indicate that the upgrade is maxed.

The main Upgrade entry remains visible only while at least one of the three
upgrade types still has a level available.

UPGRADE COSTS
-------------
Each upgrade type uses the same price progression:

Level 0 -> Level 1: 20$
Level 1 -> Level 2: 30$
Level 2 -> Level 3: 40$
Level 3: unavailable

The price is determined independently from the current level of that specific
upgrade.

ECONOMY TRANSACTION RULES
-------------------------
Use the existing money/dollar system.

Do not create a second currency or duplicate money state in the UI.

PurchaseUpgrade() must:
1. Validate wheel index.
2. Validate that the wheel is unlocked/owned.
3. Validate that the selected upgrade is below level 3.
4. Determine the price from the current level.
5. Check available money.
6. Validate the upgrade calculation/application before committing the purchase
   whenever possible.
7. Deduct the exact price only for a valid purchase.
8. Increase the selected upgrade level by exactly one.
9. Apply the new effective wheel parameters.
10. Refresh the UI.

A failed purchase must never remove money without applying the corresponding
upgrade.

UPGRADE 1 — BIGGER PADDLES
--------------------------
Target: the selected wheel's paddle geometry.

Effect per level:
- Level 0: 100% of base paddle size
- Level 1: 120% of base paddle size
- Level 2: 140% of base paddle size
- Level 3: 160% of base paddle size

Maximum bonus: +60%.

Formula:
EffectivePaddleSize = BasePaddleSize * (1.0 + 0.20 * BiggerPaddlesLevel)

IMPORTANT — VISUAL SIZE ALONE IS NOT ENOUGH

The current runtime implementation has shown that changing a visual BladeWidth
alone does not produce the required visible/physical result. Bigger Paddles must
be implemented as a real geometry change.

Required implementation:

1. Preserve immutable/base paddle dimensions.

Keep the original paddle width/height/length (whatever dimensions the active
wheel implementation actually uses) as the authoritative base values.
Do not use an already-upgraded value as the next base value.

2. Calculate effective dimensions from the base values.

For every upgrade application, calculate the complete effective paddle geometry
from the base dimensions and BiggerPaddlesLevel. Never repeatedly multiply the
current dimensions.

3. Update the visual paddle geometry.

The rendered paddle must use the calculated effective dimensions. The result
must be visibly larger at Level 1, Level 2, and Level 3.

4. Update the physical paddle collision geometry at the same time.

The FluidPolygonCollider / paddle collision polygon must be rebuilt or resized
for ONLY the selected wheel so that it covers the same effective paddle area as
the visual paddle.

The collision geometry must not remain at the original dimensions while the
visual paddle becomes larger.

5. Recalculate paddle vertices from base geometry.

If the collider uses a polygon, regenerate its local vertices from the effective
paddle width/height/length. Do not scale a previously generated upgraded polygon
again.

6. Preserve the correct local offset and rotation axis.

The enlarged paddle must remain correctly centered/anchored relative to the
wheel's rotation axis. When the wheel rotates, the enlarged collider must rotate
with the paddle exactly as the original collider did.

Pay particular attention to:
- collider center
- local position/offset
- paddle rotation angle
- distance from wheel center
- inner and outer paddle edges
- any pivot/anchor used by the visual blade

The upgrade must enlarge the paddle itself, not accidentally move the entire
paddle farther away from or closer to the wheel center.

7. Rebuild only the selected wheel's geometry.

It is acceptable to recreate/update the selected wheel's own paddle collider or
polygon representation. It is NOT acceptable to rebuild all wheel colliders or
the complete fluid simulation.

8. Verify real particle interaction.

The enlarged paddle must physically interact with water particles in the newly
added area. A successful test must show that particles can collide with the
new outer paddle area and that the larger paddle affects wheel behavior.

9. Keep the simulation instance alive.

Changing paddle geometry must not recreate PbfSolver, ParticleData, SpatialHash,
or the scene.

CORRECT BIGGER-PADDLES ACCEPTANCE CRITERIA

Bigger Paddles is only considered complete when all of the following are true:
- Level 1 visibly produces a 120% paddle size.
- Level 2 visibly produces a 140% paddle size.
- Level 3 visibly produces a 160% paddle size.
- The physical collision geometry has the same effective size as the visual
  paddle.
- The collider follows the wheel's rotation correctly.
- The enlarged outer paddle area can actually collide with particles.
- Buying another level recalculates from the original base geometry rather than
  compounding the previous level.
- Upgrading one wheel does not change another wheel.
- No fluid simulation restart occurs.

UPGRADE 2 — LESS FRICTION
-------------------------
Target: the selected wheel's friction/damping and maximum angular speed.

Effect per level:
- Level 0: base friction/damping and base max speed
- Level 1: 20% improvement
- Level 2: 40% improvement
- Level 3: 60% improvement

Recommended relationship when a lower value means less resistance:
EffectiveFriction = BaseFriction * (1.0 - 0.20 * LessFrictionLevel)
EffectiveMaxSpeed = BaseMaxSpeed * (1.0 + 0.20 * LessFrictionLevel)

Therefore:
- Level 1: friction -20%, max speed +20%
- Level 2: friction -40%, max speed +40%
- Level 3: friction -60%, max speed +60%

If the active wheel implementation uses damping semantics where a lower/higher
value has the opposite meaning, adapt the calculation to the actual variable
semantics. The gameplay result must remain less resistance and higher maximum
speed.

Runtime testing currently indicates Less Friction works and produces more energy /
better wheel performance. It should still be covered by the controlled test plan.

UPGRADE 3 — MORE EFFICIENT
---------------------------
Target: energy generation for the selected wheel.

Effect per level:
- Level 0: 100% base energy generation
- Level 1: 120%
- Level 2: 140%
- Level 3: 160%

Formula:
EffectiveEnergyGeneration = BaseEnergyGeneration *
                             (1.0 + 0.20 * MoreEfficientLevel)

The multiplier must apply only to the selected wheel's energy-generation path.
Do not multiply global energy generation or the total output of all wheels.

Current runtime testing suggests More Efficient works, but it is not yet fully
verified. A controlled before/after measurement with equivalent input is required
before marking this upgrade completely confirmed.

DATA MODEL
----------
Each wheel needs three upgrade levels:

- BiggerPaddlesLevel: 0..3
- LessFrictionLevel: 0..3
- MoreEfficientLevel: 0..3

Recommended state:
WheelUpgradeState
- int BiggerPaddlesLevel
- int LessFrictionLevel
- int MoreEfficientLevel

The state must be associated with the deterministic wheel slot/index so that
upgrading one wheel never changes another wheel.

WHEEL IDENTIFICATION
--------------------
Every Upgrade UI action must carry the wheel slot/index it belongs to.

Do not rely on:
- visual node order
- UI child index
- TileMap iteration order
- accidental current-wheel selection

The deterministic wheel-slot ordering from WHEEL_PROGRESSION_GAMEPLAN.txt
remains authoritative.

RECOMMENDED API
---------------
WaterWheelManager / wheel progression layer:
- HasAvailableUpgrades(int wheelIndex)
- GetUpgradeLevel(int wheelIndex, WheelUpgradeType type)
- GetUpgradePrice(int wheelIndex, WheelUpgradeType type)
- CanPurchaseUpgrade(int wheelIndex, WheelUpgradeType type)
- PurchaseUpgrade(int wheelIndex, WheelUpgradeType type)

Possible enum:
- BiggerPaddles
- LessFriction
- MoreEfficient

UPGRADE APPLICATION
-------------------
The wheel implementation should expose or internally calculate immutable base
values and effective values for:

- BasePaddleSize / base paddle geometry
- BaseFriction / BaseDamping
- BaseMaxSpeed
- BaseEnergyGeneration

Avoid permanently modifying the base values after every purchase.

Instead:
1. Keep immutable/base values.
2. Store upgrade levels.
3. Recalculate effective values whenever an upgrade level changes.
4. Apply only the selected wheel's changes.

Recommended conceptual pattern:

ApplyUpgrades()
{
    PaddleSize = CalculateEffectivePaddleSize();
    RebuildOrResizeSelectedWheelPaddleCollider();
    Friction = CalculateEffectiveFriction();
    MaxSpeed = CalculateEffectiveMaxSpeed();
    EnergyGeneration = CalculateEffectiveEnergyGeneration();
}

This prevents compounding errors and duplicate application.

RUNTIME BEHAVIOR
----------------
An upgrade purchased while the simulation is running must apply immediately.

Existing particles continue using the same simulation instance.

Expected behavior:
- Bigger Paddles changes visual AND physical paddle geometry in place.
- Less Friction changes that wheel's resistance and speed limit immediately.
- More Efficient changes that wheel's energy output immediately.

No scene reload is allowed.

UI IMPLEMENTATION
-----------------
UPGRADE ENTRY
- Show an Upgrade entry if HasAvailableUpgrades(wheelIndex) is true.
- Hide it once all three upgrade types reach level 3.
- The first owned wheel must show it automatically while upgrades remain.

UPGRADE WINDOW
- Exactly three rows.
- Order: Bigger Paddles, Less Friction, More Efficient.
- Each row has its own purchase button.
- Prices update independently to 20$, 30$, or 40$.
- Maxed rows show MAX or otherwise become unavailable.
- The window refreshes after every purchase.
- The window closes when all three upgrade types are maxed.

UI LAYERING REQUIREMENT
- Create the Upgrade UI using the working Buy UI creation approach.
- Keep the Upgrade UI on the current Main scene, outside the SimulationViewport.
- Use a top-most ZIndex so Environment TileMapLayer cannot cover it.
- Do not move it into FluidSimulation/GameView/SimulationViewport.

STYLE
-----
Reuse the existing Buy Window visual language:
- same background treatment
- same borders
- same button style
- same typography
- same spacing conventions
- same UI settings/configuration where applicable

Do not introduce a separate visual design system for upgrades.

PERSISTENCE
-----------
Upgrade levels must eventually persist per wheel.

Recommended saved state contains, for each wheel slot:
- BiggerPaddlesLevel
- LessFrictionLevel
- MoreEfficientLevel

Do not save runtime wheel nodes, colliders, particle state, or solver state.

Startup order when persistence is available:
1. Initialize gameplay systems.
2. Discover wheel positions.
3. Load wheel ownership.
4. Load per-wheel upgrade levels.
5. Create unlocked wheels only.
6. Apply each wheel's saved upgrades, including visual and physical paddle
   geometry.
7. Start/continue normal simulation.

If persistence is not yet complete, keep the upgrade state architecture
compatible with the planned save system instead of creating a temporary
incompatible format.

PERFORMANCE SAFETY
------------------
Upgrades must not introduce a recurring expensive operation.

Rules:
- No per-frame TileMap scanning.
- No per-frame searching for the selected wheel.
- No rebuilding all wheel colliders after an upgrade.
- No rebuilding the PBF solver.
- No complete simulation restart.
- No repeated multiplication of already-upgraded values every frame.
- Rebuild/update only the selected wheel's paddle geometry when Bigger Paddles
  changes.

TEST PLAN
---------

TEST 1 — INITIAL UPGRADE WINDOW
- Start a new game.
- Confirm the first available/owned wheel exists.
- Confirm an Upgrade entry is visible.
- Confirm the entry disappears only when all three upgrades are maxed.

TEST 2 — UPGRADE WINDOW CONTENT
- Open Upgrade.
- Confirm exactly three rows exist.
- Confirm order: Bigger Paddles, Less Friction, More Efficient.
- Confirm each row has its own price button.
- Confirm initial prices are 20$.

TEST 3 — MONEY DEDUCTION
- Purchase an upgrade with sufficient money.
- Confirm the exact upgrade price is deducted.
- Confirm the correct upgrade level increases by one.
- Confirm no unrelated upgrade level changes.
- Confirm an invalid/insufficient-money purchase deducts nothing.

TEST 4 — BIGGER PADDLES VISUAL
- Measure/record base paddle dimensions.
- Purchase level 1.
- Confirm the paddle is visibly 120% of base.
- Purchase level 2.
- Confirm the paddle is visibly 140% of base.
- Purchase level 3.
- Confirm the paddle is visibly 160% of base.
- Attempt level 4 and confirm it is rejected.

TEST 5 — BIGGER PADDLES PHYSICS
- Compare the visual paddle and physical collider at Level 0.
- Purchase Level 1 and confirm the collider grows to the same effective size.
- Repeat for Levels 2 and 3.
- Confirm the collider remains correctly centered on the wheel.
- Rotate the wheel and confirm the collider follows the paddle.
- Confirm particles can collide with the newly added outer paddle area.
- Confirm no other wheel's collider changes.
- Confirm no simulation restart occurs.

TEST 6 — BIGGER PADDLES NO COMPOUNDING
- Record base paddle dimensions.
- Purchase Level 1, then Level 2, then Level 3.
- Confirm values are exactly 120%, 140%, 160% of BASE, not 120%, then
  168%, then another compounded value.
- Reapply/refresh the upgrade state and confirm the same values remain.

TEST 7 — LESS FRICTION
- Purchase level 1 and confirm resistance/friction is reduced by 20% and max
  speed increases by 20%.
- Purchase level 2 and confirm 40% total improvement.
- Purchase level 3 and confirm 60% total improvement.
- Attempt level 4 and confirm it is rejected.

TEST 8 — MORE EFFICIENT
- Measure baseline energy generation under equivalent conditions.
- Purchase level 1.
- Repeat the same measurement under equivalent conditions.
- Confirm approximately +20% output for the selected wheel.
- Repeat for Levels 2 and 3 and confirm +40% and +60% relative to base.
- Confirm other wheels remain unchanged.

TEST 9 — INDEPENDENT UPGRADES
- Upgrade Bigger Paddles on wheel 1.
- Upgrade Less Friction on wheel 2.
- Upgrade More Efficient on wheel 3.
- Confirm each wheel retains only its own upgrades and effective values.

TEST 10 — PRICE PROGRESSION
For each upgrade type:
- Level 0 purchase costs 20$.
- After Level 1, next price is 30$.
- After Level 2, next price is 40$.
- After Level 3, purchase is unavailable.

TEST 11 — RUNTIME SAFETY
- Run the simulation with active water.
- Purchase upgrades while particles are moving.
- Confirm no simulation reset occurs.
- Confirm existing particles remain active.
- Confirm no large artificial energy spike occurs.
- Confirm no wheel duplication occurs.

TEST 12 — SAVE/LOAD
- Once persistence exists, upgrade several values on several wheels.
- Restart the game.
- Confirm every wheel restores its own upgrade levels.
- Confirm effective visual and physical paddle parameters match the saved levels.

TEST 13 — PERFORMANCE
- Compare FPS before and after upgrades.
- Confirm no recurring performance cost is introduced.
- Confirm upgrading one wheel does not rebuild all wheel geometry.

TEST 14 — MAXED STATE
- Max all three upgrades on a wheel.
- Confirm all three purchase buttons are unavailable.
- Confirm the main Upgrade entry for that wheel is hidden/disabled.
- Confirm no further money can be spent on that wheel's upgrades.

COMPLETION CRITERIA
-------------------
Wheel Upgrades are complete only when:
- all purchases correctly deduct money;
- Bigger Paddles is visually and physically correct;
- Less Friction is verified against its intended physics values;
- More Efficient is verified with controlled measurements;
- upgrades remain independent per wheel;
- max levels and prices are enforced;
- runtime upgrades do not restart or rebuild the fluid simulation;
- performance remains acceptable;
- persistence is integrated when the project's save system is available.
